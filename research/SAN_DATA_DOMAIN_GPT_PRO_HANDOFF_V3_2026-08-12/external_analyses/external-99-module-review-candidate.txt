The correct horizontal **Data and Analytics domain model** is now a deterministic registry of **99 composable candidate libraries across 11 domains**, with open-ended data types, source systems, formats, codecs, methods, formulas, recipes, products, and maintenance procedures kept as configuration/reference packs rather than being miscast as thousands of sovereign libraries.

# 1. The governing decomposition

The model now has three independent axes:

```text
┌─────────────────────────────────────────────────────────────────┐

└─────────────────────────────┬───────────────────────────────────┘
                              │ configured by
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│ AXIS 2 — OPEN-WORLD REFERENCE AND CONFIGURATION PACKS           │
│                                                                 │
│ data types              source families and products             │
│ file formats            encodings and codecs                     │
│ transformation ops      analytical methods                       │
│ formulas                recipes                                  │
│ movement modes          storage patterns                         │
│ maintenance ops         change/evolution events                  │
│ provider offers         conformance profiles                     │
└─────────────────────────────┬───────────────────────────────────┘
                              │ composed by
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│ AXIS 3 — INDUSTRY AND APPLICATION VERTICAL PACKS                │
│                                                                 │
│ ontology contexts       business capabilities                    │
│ data products           industry metrics and features            │
│ analytical recipes      source bindings                          │
│ reference publications  policies                                 │
│ experience places       provider requirements                    │
└─────────────────────────────────────────────────────────────────┘
```

This follows the uploaded lifecycle requirement: the decomposition is only a review candidate until alternatives, ownership, seams, adversarial review, implementation, execution evidence, and independent certification have been completed. 

It also preserves the Data Atlas’s load-bearing distinction among physical encoding, logical interpretation, and semantic meaning. Those layers are related, but one must never impersonate another merely because a database driver returned a cheerful type name.

```text

    ├── Policy packs
```

For example:

```text
SPORTS SOLUTION PACK
    athlete, team, match and competition ontology
    player-performance metrics
    possession and shot-event recipes
    tracking-coordinate reference packs
    injury-risk features
    sports analyst workspaces

OIL AND GAS SOLUTION PACK
    well, reservoir, field and equipment ontology
    production and decline metrics
    pressure/transient and maintenance recipes
    geological and unit reference packs
    failure-prediction features
    operations and reservoir-engineer workspaces

UNCHANGED
    collection and cut semantics
    source observation
    snapshot and continuation
    streaming and finality
    time-series and spatial algebra

    statistical-study semantics
    incremental computation
    analytical publication
```

Customization is therefore the lawful assignment of declared decisions and pack inputs, not a fork of the library with `sports_mode = false` changed to `oil_mode = true`. Humans have tried that general strategy before. The repositories remember.

`DAT-STREAM-TABLE-DUALITY` is an important addition. A dynamic table may be represented through a changelog, and a changelog may be interpreted as a changing table, but only under explicit key, ordering, and change-mode conditions. Flink itself distinguishes insert-only, upsert, and retract modes rather than pretending “stream” and “table” are interchangeable nouns. ([[Apache Nightlies](https://nightlies.apache.org/flink/flink-docs-stable/docs/concepts/sql-table-concepts/dynamic_tables/)][1])

The supplied 300-name analytics taxonomy itself notes that the terms overlap and that the better representation is `decision mode + technique + data source + business domain`. 

`DAT-STATISTICAL-POPULATION-SAMPLING` was separated from acquisition-side partial observation because a target population, sampling frame, inclusion probabilities, weights, strata, and clusters define inferential scope. A source API truncating at 10,000 records does not magically become a statistically designed sample. NIST likewise treats the sampling scheme as the specification of what data are obtained and how they are obtained. ([[NIST](https://www.itl.nist.gov/div898/handbook/ppc/section3/ppc332.htm)][5])

**7 libraries**

```text

DAT-CLEAN-ROOM-ANALYSIS
DAT-VIRTUAL-DATA-RELATION
```

`DAT-VIRTUAL-DATA-RELATION` was added for provider-neutral relations whose rows remain remotely backed or federated.

The compiler owns whether to push down, materialize, or execute locally. Providers publish exact capabilities. DAT owns the meaning and disclosure posture of the virtual relation.

Trino’s connector contract demonstrates why this cannot be a generic `pushdown = true`: individual operations may be unsupported, have no effect, or be deliberately kept local when remote execution risks correctness. ([[Trino](https://trino.io/docs/current/develop/connectors.html)][6])

`DAT-ANALYTICAL-CACHE` was removed as a sovereign DAT owner. Cache keys, invalidation, eviction, and coherence belong to Client-Facing Contract, Runtime Mechanism, Resource Guarantees, and Desired-State Control.
