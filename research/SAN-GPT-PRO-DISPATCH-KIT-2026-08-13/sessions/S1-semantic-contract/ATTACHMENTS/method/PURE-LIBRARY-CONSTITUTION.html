1. Prime library law R§1.1

Repository source-authority law

The old SAN toolkit is deprecated evidence, explicitly including toolkit/factory/**, toolkit/foundation/**, old chassis/kernel/platform families and their local contracts, registries, envelopes, compilers and IRs. A canonical candidate MUST NOT import, wrap, extend, or place new canonical machinery in those trees. Existing coupling to them is a migration defect, not supplier authority.

Recovered semantics require a symbol-level disposition and fresh proof in the new owner. Cross-domain replacements belong in a separately ratified greenfield platform boundary; old Factory is neither that boundary nor a temporary home. Compilation, workspace membership, path, documentation, popularity and current consumers do not promote deprecated code.

A toolkit library is valid only when it is simultaneously:

PURE semantic behavior is deterministic and free of ambient effects BOUNDED it owns one coherent semantic closure and depends only on public contracts DECISION-COMPLETE every behavior-affecting choice is either a named invariant or an exposed, typed, authorized decision COMPOSABLE required and provided contracts are typed, versioned, bindable and recursively encapsulable

Customization is not an escape hatch around the library. It is the lawful assignment of the library's exposed decision surface. Composition is not a caller importing sibling internals. It is the binding of published contracts. Consequently:

  • a pure library with hidden decisions is incomplete;
  • a configurable library with ambient I/O is not pure;
  • a reusable crate without a sovereign boundary is not a family;
  • a bounded family without typed imports and exports is not composable;
  • a declaration path producing semantics unavailable through the native Rust API is a competing implementation;
  • a public knob that can weaken a family invariant is invalid customization.

These four properties MUST be proven together. Cards, IR, kernel seams, ports, adapters and runtimes are conditional mechanisms; none substitutes for any of the four.

Applicability. These rules bind horizontal software domains — Identity, Authentication, Federation, Tenancy, Authority, Time, Truth, Process, Work, Money, Evidence, Delivery, Observability. Vertical business domains — Sales Order, Insurance Claim, Clinical Trial, Employee Case — are application content; they MAY publish vertical extension libraries but are not horizontal toolkit families.

5. The nine closures C§I

A family specification is complete iff every applicable closure is total. Each is an independent mapping; a family may declare one inapplicable only with a semantic reason and a structural proof.

6. The decision model C§II

6.1 The correction

The single F/A/O/J/E/R/D column used by every existing specification conflates two orthogonal questions: who is entitled to decide, and how the value comes to be resolved. The consequence is real: a row can read as though a runtime observation has authority to decide a lifetime class, when observation may only supply evidence under an already-admitted policy.

Every decision key MUST carry three coordinates: authority, mode, phase.

6.2 Authority, mode, phase

enum DecisionAuthority {          enum ResolutionMode {
    FamilyConstitution,               Fixed,       // invariant; nobody varies it
    ApplicationOwner,                 Provided,    // authored by its authority
    OrganizationPolicy,               Defaulted,   // named profile, with provenance
    JurisdictionAuthority,            Derived,     // planner-computed; unauthorable
    TenantAuthority,                  Delegated,   // a sibling family owns it
    EnvironmentOperator,              Observed,    // EVIDENCE, never a decision
    ReferenceDataAuthority,           Impossible,  // refused by a named impossibility
    ExtensionCertifier,               Gap,         // openly unresolved; blocks production
}                                 }

enum BindingPhase {
    FamilyEdition, PackageClosure, ApplicationRelease,
    TenantBinding, EnvironmentBinding, RuntimeEvaluation,
}

Rules

  1. Every key MUST name exactly one authority and one mode.
  2. Observed MUST NOT appear with an authority other than EnvironmentOperator or ReferenceDataAuthority, and its value MUST feed a decision already admitted under another key.
  3. Fixed MUST pair with FamilyConstitution.
  4. Derived MUST name the derivation and MUST NOT be authorable anywhere.
  5. Gap MUST carry a case ID and a reopening rule, and MUST block production use of the profile it affects.
  6. Bounded selection is an authority pair with a stated ordering — ApplicationOwner ≤ OrganizationPolicy — never a single hyphenated code.
  7. NEW An authority code with zero members in a family's catalog MUST be removed from that family's vocabulary. Two families carried an R code that no key used and that two of their own sections defined contradictorily.

6.3 Two-stage closure C§2.4c

A decision at phase EnvironmentBinding or later MUST NOT appear in a portable plan; the plan carries an unbound slot and a requirement. Every family whose catalog contains an environment-phase key MUST split its closure.

FamilySpec + semantic policies ▼ PortableFamilyPlan semantic decisions · requirements · UNBOUND slots ▼ + environment catalog + certified offers BoundFamilyPlan provider · resource · reference-data bindings ▼ + runtime observations individual pure decisions A single close(spec, policies) -> Plan that silently absorbs a leap-table edition, a probe cadence, an arbiter endpoint or an issuance locus has put a DEPLOYMENT FACT inside a PORTABLE ARTIFACT. Runtime observations NEVER enter a sealed plan. The plan declares which observations are required and how they bear on an admitted decision.

6.4 Merge contracts — the archetype is not the specification

Six algebras: exactly_one · most_restrictive · set_intersection · set_union · bounded_override · derived_only. Generic recursive merge, file-order precedence and last-writer-wins are forbidden. Order-independent closure is mandatory: reordering inputs yields the same plan digest or a stable conflict.

Three algebras, never one generic “merge”
Operation Question Required result
Contribution merge How do independently authored values for one decision key fold into one resolved value? value or stable conflict; associative/commutative/idempotent exactly where claimed
Requirement join How do several consumers' constraints combine into one requirement? stronger requirement or incompatibility proof; the family owns the requirement order
Offer satisfaction Does one provided contract meet one joined requirement under this scope and edition? typed SatisfactionProof or typed refusal with the unmet clause; never bool

A descriptor MUST name these independently when they apply. Reusing one MergeContract field for all three is a metamodel defect. A family may delegate the storage shape to the shared contract vocabulary, but it owns the partial orders, proof rules and refusal semantics of its native values.

6.5 Naming hygiene C§2.6

A family MUST NOT reuse a bare noun already load-bearing in another family. Standing instance: Assurance belongs to Authentication — the strength of an identity or authenticator proof. A family meaning probabilistic uniqueness MUST say UniquenessBasis, UniquenessAssurance or CollisionAssurance.

7. The family surface C§III

7.1 Shape-indexed, not fixed

A family publishes a surface manifest with eight lists. Any list may be empty only with a stated reason. 

FamilySurface {
    constructors,   // admit or create values

7.1.1 Universal publication obligations

Shape-indexed does not mean that a family may omit the doors needed to use, compose, inspect and verify the shapes it does own. Every family MUST publish the following logical surfaces. They may be modules, associated functions, constants or generated projections; this is not a mandatory crate topology or a demand for one literal function name per row.

parse / format the family owns an admitted external representation

A family with none of those conditions ships none of those functions. Money requires construction, arithmetic, allocation, rounding and formatting and no cards. Instant requires no decide/evolve. A reconciling family requires convergence semantics and no timeless answer vocabulary.

Each sovereign query class publishes one total answer vocabulary enumerating every honest outcome including the sad ones. A family with several epistemically different operations publishes several vocabularies: a parse result, a construction result, a current resolution, an allocation result and a compatibility verdict are not one enum.

Option<T> MUST NOT stand in for an answer vocabulary. Collapsing two honest outcomes into one MUST be justified against a named failure.

7.4 The trait test

Traits are not banned; effectful and ambient capability traits are.

ADMISSIBLE a pure algorithm strategy, IF AND ONLY IF it is narrow · versioned · deterministic · carries an implementation identity and a certificate · has laws FORBIDDEN any trait that can conceal I/O, or that admits a second semantic implementation of the family's own question PREFER immutable supplied views, or an explicit multi-round query plan (NeedsMore { next_query }), over any trait a caller could implement with a network call

The test is not "is it pure today" but "can it conceal an effect, or fork the semantics, tomorrow."

A family MAY expose a static generic surface and an erased dynamic surface. Both MUST close to the same plan and produce identical canonical bytes, proven by equivalence fixtures. The criterion:

a distinction that must fail at compile time is a type parameter;
a distinction a declaration selects is data.

7.6 Execution algebras

A family defines no driver. The platform provides one generic driver per execution algebra — aggregate (decide/evolve), process, case, conversation, reconciler, analytical — because sharing context, receipts and persistence contracts does not make progress semantics identical.

Start with modules. A crate exists only at a real boundary. No crate list is a template. Every split MUST publish its asymmetric-consumer proof and MUST collapse if that consumer graph does not materialize. Full test in §11.

7.8 The artifact-class rule NEW

Ratified once here because two families wrote it wrongly

The purity clause, in full

Time, entropy, observations, reference data and policy snapshots MUST be explicit inputs. Pure code MUST NOT read clocks, randomness, environment variables, files, network state, global registries or mutable process state.

Domain refusals, infrastructure faults and programming defects MUST be separate types.

8.2A Rust realization law

Rust features are selected to enforce a named obligation, never to satisfy an anatomy template. Stable Rust 2024 is the default. Native values use private fields, admitted construction and exhaustive semantic enums. APIs borrow inputs and return owned values unless a documented lifetime/allocation case requires another shape. Closed hot semantics use static dispatch; runtime-selected closed alternatives use enums; trait objects require a genuinely open heterogeneous set. Traits are owned by the capability consumer and may not conceal effects or ambient authority.

Arithmetic overflow, narrowing, rounding and approximation are explicit laws; release-mode wrapping and semantic as casts are forbidden. Pure paths contain no async executor, lock, atomic, mutable global, ambient cache or interior-mutability escape. unsafe is forbidden by default and, where independently justified, is isolated behind a narrow safe facade with a written safety invariant. Cargo features are additive portability/capability switches only; semantic species, profiles, algorithms, defaults and policies are typed data. repr(Rust) is never a persistence, wire or FFI contract.

Macros remove proven syntax repetition; they do not become family-local semantic compilers. Proc-macro dependencies remain outside ordinary runtime paths. Foundation code uses core/alloc when that follows naturally from its dependency graph, but no speculative no_std promise justifies custom replacements for mature standard or ecosystem types.

8.3 Declarable decision surface

11. Crate boundaries R§17 + C§3.7 RESOLVED

The two sources agreed in spirit and differed in emphasis: the Rules gave a seven-item justification list, the Constitution said modules first and no template. Unified: the justification list is the test the "no template" rule demands.

START WITH MODULES. 12b. Nine further universal rules NEW

An independently drafted rule set (Edition 4, 76 numbered rules) was reconciled against this merge on 2026-08-05. Most of it restates §§1–12 in a different order. Nine rules stated something neither source document did, and they are adopted here with their reasons, because in each case the reason is the load-bearing part.

# Rule Why — and where the absence would have shown
U1 Purity means explicit causality, not zero dependencies. Semantic outputs depend only on explicit canonical inputs. Pure, audited, semantically subordinate dependencies are permitted; ambient authority and effectful dependencies are not Reimplementing Unicode, decimal arithmetic, cryptographic verification or time values merely to claim dependencylessness increases risk without increasing semantic independence. §8.2's purity clause says what is forbidden and never said this
U2 Semantic cores have no ambient authority. A library receives only the principal, actor, subject, tenant, purpose, authority proof, deadline, idempotency identity or budget it actually requires A giant PlatformContext conceals authority and lets a library depend on capabilities it never declared. This is the authority analogue of ambient I/O, and neither source forbade it
U3 Resolver-like APIs are total. They return a closed public fate — alive, redirected, retired, redacted, forbidden, unavailable, unknown — and never an undifferentiated null Different kinds of absence have different authority, retry, disclosure and recovery semantics. §7.3 banned Option<T> as an answer vocabulary; this states the positive obligation
U4 Untyped semantic escape hatches are forbidden. No raw String, arbitrary JSON value, generic map or integer may replace a semantic type the model already owns Every untyped escape creates a second undocumented language outside the family's laws. §8.4 forbade this in cards; it applies to every surface
U5 Envelopes are boundary artifacts, not internal value containers. Use them only across asynchronous, process, integration or deployment boundaries; internal pure calls use native typed values Serializing every internal operation through a generic envelope destroys type precision and adds accidental coupling — the exact mechanism by which a pure core acquires a runtime shape
U6 Security, tenancy, privacy and authority metadata survive every projection. Scope, sensitivity, purpose, retention, residency, erasure, logging, caching and authority-bearing status travel with the value A generated API, cache, event, index or UI must not accidentally erase obligations present in the source model. The 19 dimensions require the metadata to exist; nothing required it to survive derivation
U7 Production and SOTA are evidence claims, not adjectives. Production certification requires production adapters, boot guards, health, security, migration, recovery and operational evidence. A state-of-the-art claim additionally requires dated standards traceability, practice coverage, failure closure, vectors, properties, fuzzing, mutation tests, cross-language parity, performance evidence, threat modelling and a gap ledger A large document, a passing compile or an impressive vocabulary proves neither. Four of five family specifications used "implementation-grade" or "state of the art" as adjectives; §17 defined the levels without forbidding the adjective
U8 Legacy compatibility is an explicit requirement, never an automatic burden. Preserve it only where persisted values, published consumers, issued evidence or contractual commitments require it Carrying unneeded historical APIs into a greenfield family corrupts the new boundary; discarding required historical interpretation corrupts users' reality. Both failures were available and neither was named
U9 A family is complete only when no consumer requires a hidden decision or an implementation fork. Every supported use is realizable through native types, species, profiles, policies, passports, explicit material and certified extensions The ultimate span test: variation changes selections and data, not the authoritative implementation. §15's theorem proves internal totality; this proves the family actually spans its consumers
On the reconciliation itself

The two rule sets agree substantially, which is worth more than either alone: they were drafted independently and converge on sovereign questions, negative charters, decision authority, typed passports, asymmetric-consumer crate proofs, laws with negative twins, owned gaps and staged certification.

Where they differ, each supplies what the other lacks. Edition 4 is stronger on rules — 76 numbered obligations, each with a stated reason, which makes it teachable. This document is stronger on techniques — the nine closures with their specimens, the nineteen conformance dimensions, the eighteen audit rules and the sixteen-step golden thread, which make it executable.

A rule without a technique is advice; a technique without a rule is a habit. The nine above close the gap on the rule side; §§5, 14 and 16 remain the executable half.

14.1 The assurance sweeps folded 2026-08-06

The audit rules above are made executable by fixed enumeration procedures. These are not advisory: a family review that skipped an applicable sweep has not been reviewed. Provenance: HAZOP (IEC 61882), STPA (Leveson), sufficient completeness (Guttag–Horning), protocol conformance (Chow), covering arrays (NIST), mutation (DeMillo–Lipton–Sayward), feature models (FODA), theoretical saturation (Glaser–Strauss), bidirectional traceability (DO-178C/ISO 26262). Proportionality rule. The cheap sweeps bind every family: constructor × observer sufficiency, duals/zeros/idempotents, API-manifest closure, HAZOP guide words on seams, generators 1–5 and 9–12. The expensive sweeps bind only where their subject exists: total State × Command matrices and STPA where state or a control loop exists; covering arrays where the decision lattice is large; mutation evidence where certification is claimed. A twelve-function value library does not need a covering array; a stateful family without its matrix has not been specified.

API-manifest closure is bidirectional and mechanical. The specification's operation manifest and the crate's generated public-API record (rustdoc JSON / public-api digest) are diffed both ways: a specified operation with no public symbol is an implementation defect; a public symbol with no manifest row is a specification defect. The cardinality is exact: each public semantic symbol has one stable operation/observer descriptor. A convenience table may group related methods for readers, but a group ID, numeric range or prose list cannot stand in for the child descriptors consumed by the API diff. The constructor × observer grid then proves sufficiency: every constructible value is fully observable, and every observer is defined (or refuses) on every constructor's output. Frozen per-edition API digests plus semver checking anchor evolution. Until the shared compiler exists this diff MAY be run manually; it MUST be run.

No silent state. A family's state class (none · process-local · durable · coordinated · external-authority) is declared at classification and human-ratified. A pure family that needs persistence emits a typed storage requirement into the sealed closure, unbound until a provider offer satisfies it with proof. Nothing may be stored at runtime that is not visible as a requirement in the sealed artifact: generic runtimes execute plans, not ambient intentions.

17. Staged certification R§21

Completion has four independent levels. A pure family is not held incomplete because the application compiler, loader or a production provider has not yet been built.

17.1 Level 1 — library-conformant

Every charter term maps to an exact Rust symbol · every law has an executable twin · every public decision is pure and deterministic · every behavior-affecting branch is classified · the decision descriptor is exhaustive and deterministic · every input has authority, absence, default, canonical and digest semantics · every output names a consumer · every configurable choice is reachable through typed data · declared and direct-Rust choices admit to the same native type · no configurable choice can weaken a signature law · every cross-family edge uses a legal contract · the composition descriptor declares every contract, capability, extension, lowerer and operational requirement · the native API compiles without compiler, runtime or adapter dependencies · declaration and direct-Rust paths have equivalence fixtures · target-IR lowering has coverage evidence where present · a stateful family has one canonical-kernel contribution and native-versus-kernel equivalence tests · every pure callable has a versioned function contract · every external implementation passes its conformance laws · every unsupported case is an explicit owned gap · dependency, forbidden-import, formatting, Clippy and test gates pass.

Compilation alone is not library-conformance evidence.

17.2 Level 2 — composition-certified

The ordinary application linker composes it with at least one other family · missing, duplicate and incompatible contracts are rejected before boot · recursive composites expose only authorized child decisions · all hidden child decisions are resolved or explicitly deferred · direct-family and composed behavior have equivalence fixtures · no family-specific linker branch or bespoke glue is required.

17.3 Level 3 — runtime-certified

Delivery components register runtime-part and adapter descriptors · a sealed closure and signed recipe boot through the generic loader · native decisions and kernel execution are equivalent · every required port is bound to an implementation passing its law suite · unsafe development defaults are rejected in production mode.

A family with no runtime effects MAY declare this level inapplicable with an executable proof of purity.

17.4 Level 4 — production-certified

Every selected provider is production eligible and certified · boot, migration, health, telemetry, evidence and operational guards pass · security, tenancy, privacy, performance and failure requirements are met · at least two materially different application witnesses use the family unchanged, unless it is a uniform platform invariant.

20. Ratification, amendment and order

20.1 Ratification

A family passes through three distinct states. A design candidate is research and is not implementation authority. An implementation candidate has passed inventory, charter, ontology, decision-surface, seam, gap-ledger and crate-boundary review; it authorizes Rust implementation so the executable evidence can be produced, but it is not selectable by an application. A family is Level-1 library-conformant only when §§4–7, §14 and §17.1 are satisfied and the evidence is recorded in the family specification. Level 2 additionally requires the cross-family golden thread. This sequencing is mandatory: prose cannot certify code that does not exist, and code cannot silently define semantics absent from the reviewed candidate.

20.2 Amendment

Shared vocabularies — decision authorities, resolution modes, binding phases, merge algebras, refusal taxonomy, card skeleton, execution algebras, contract kinds — are owned by this document. A family MAY use them and MUST NOT extend them. Adding an entry requires two independent family witnesses and a written ruling.

20.3 Amendments are folded, never appended NEW

The rule this merge exists to demonstrate

An amendment to a specification MUST be folded into the body before ratification. An appendix that corrects the body is a defect, not a correction.

Every family carrying a "Part Z — constitution conformance" appendix had its body and appendix disagree: commands added to no aggregate, refusals in no class, decision keys in no catalog, states in no enum, gaps in no ledger. In one document the appendix added two decision keys while four other sections continued to state the old total.

The same applied to the two documents merged here. A precedence clause between two normative texts is the institutional form of the same defect — and it is why this document has no sibling.
