SAN Software-Domain Library Method

Edition 4 · review candidate · 2026-08-07 · Constitution · Kernel · FAMILY-SPECS ledger · Reference spec · Program dashboard

Purpose. A phase-by-phase method for deciding whether a concern deserves a pure Rust library, discovering its complete semantics, splitting it at real DDD boundaries, exposing every lawful decision, and proving composition without duplicating platform machinery in each domain.

Authority. PURE-LIBRARY-CONSTITUTION.html remains the sole normative library law. The derived R01–R44 checklist is the operational gate. This document defines the review and realization procedure. It does not add semantic law and supersedes SPEC-METHOD.html edition 1.

Prime correction. The 28 DDD artifacts are an applicability audit. They are not 28 mandatory products. A census of 100 nouns is evidence about the world, not evidence that one proposed family owns them.

Greenfield rule. New canonical libraries are designed from product intent, domain evidence, the Constitution and current authoritative sources. The old SAN toolkit is deprecated, explicitly including toolkit/factory/**, toolkit/foundation/**, old chassis/kernel/platform families and their local contracts, registries, envelopes, compilers and IRs. Deprecated code is read-only evidence during specification work. It is neither a supplier nor an implementation destination; its names, crates, APIs and boundaries are not design constraints.

Rule: ontology breadth is retained. Ownership is not inferred from breadth. The agent completes the research lanes, partitions every observed term by semantic owner and disposition, and designs only the selected closure.

A provider-bound plan is not provider-neutral. Customer business records belong to the tenant runtime and are not part of any of these artifacts.

2.3 IR ruling

There is one canonical application semantic graph for products, contracts, decisions, provenance, obligations, conflicts and gaps. Executable representations remain target-owned IRs for Data, Behavior, Event, Read, Experience, Integration, Operations, Migration and Assurance. A single executable IR is rejected because target semantics and consumers differ.

2.4 Standards and implementation evidence protocol

Standards and dependency claims are dated evidence. Each adopted mechanism or semantic rule must have one review record with the fields below. A search result, secondary summary, crate popularity count or repository README is not normative evidence.

FieldRequired content
Questionthe exact semantic or mechanical decision being supported
Primary authoritystandards body specification, official language/library documentation, peer-reviewed paper, or authoritative upstream source
Edition postureidentifier, publication date, status, errata, supersession and access date
Adoption rulingadopt · adapt · wrap · reference · reject, with the owned and delegated semantics stated
Rust mechanismcrate and version, maintained status, MSRV, feature/dependency surface, unsafe posture, license and relevant API
Evidenceofficial vectors/corpora, differential or interoperability evidence, known limits and unsupported cases

Primary sources take precedence over recollection and secondary commentary. A current claim is rechecked when it can change independently of the repository. Standards supply subordinate mechanics or published-language constraints; they do not silently become the family's semantic authority.

3.2 Status vocabularies

Implementation inventory uses exactly REAL, PARTIAL, STUB, SPEC_ONLY, DUPLICATE, DEAD or UNKNOWN. Rule review uses exactly PASS, PARTIAL, FAIL, INAPPLICABLE with a structural reason, or UNKNOWN. Certification uses exactly none, library-conformant, composition-certified, runtime-certified or production-certified. These vocabularies answer different questions and are not interchangeable.

3.3 Specification and code authority

research record → review candidate specification → implementation candidate specification → Rust realization + executable evidence → library-conformant edition → composition/runtime/production certification, when applicable
  • A review candidate records unresolved alternatives and does not authorize implementation claims.
  • An implementation candidate has passed S0–S7 and is the sole semantic target for Rust realization.
  • Rust code is evidence only for the exact specification edition and digest it implements.
  • A code/spec mismatch changes the implementation status to PARTIAL; passing legacy tests does not overrule the normative specification.
  • A specification amendment records the changed law, decision, seam, artifact, compatibility consequence, affected symbols and required evidence refresh.
  • Generated manifests and evidence may be replaced only by regeneration from the authoritative descriptors and code revision.

Saturation rule

Research proceeds by materially distinct context, not by a target source count. Each additional context is logged with the semantic delta it contributed. Saturation is reached only when the latest distinct contexts contribute no new native term, invariant, decision, state transition, refusal, seam, evolution case or named gap. Repeated mechanisms without semantic delta are recorded as corroboration. The agent reports uncovered lanes and confidence; it does not declare exhaustion when a lane was not investigated.

The agent does not ask for information it can establish from sources or the repository. It does not infer product authority, acceptable risk or contested defaults from technical practice. A question presents the evidence, available decisions and consequences.

3.5 Greenfield realization and legacy disposition

Fail-closed source boundary. No canonical candidate may depend on or add canonical machinery to the old toolkit. In particular, Factory is deprecated: shared descriptors, contract headers, composition algebras, IR and linking machinery must be designed in a separately ratified greenfield platform boundary. An existing dependency into the old toolkit is recorded as a migration defect, not accepted as a supplier seam.
StageLegacy-tree rule
S0 Inventoryread only; recover requirements, consumers, persisted representations, issued proofs, failures, duplicates and potentially reusable subordinate mechanics
S1–S4 Classification/boundarylegacy names, crate count, layering and ownership do not constrain the candidate; each retained concept requires independent semantic evidence
S5–S7 Specificationdefine the complete greenfield semantics, decision space, seams, evolution and resource laws; do not patch legacy APIs or write compatibility clauses without a proven commitment
S8 Rust realizationimplement in the new canonical family or ratified greenfield platform location; do not depend on deprecated internals or place replacements in old Factory/Foundation; prefer current audited external crates for subordinate mechanics
S9 Evidenceprove the new implementation directly; a wrapper around legacy code or a passing legacy suite is not new-family conformance
Post-conformance migrationwrite explicit import, upcast, compatibility or anti-corruption adapters only for proven persisted values, issued evidence or contractual consumers

A legacy symbol may be transplanted only after a disposition record identifies the exact symbol, semantic equivalence, dependency posture, safety/resource behavior, required refactor and evidence. The implementation is then owned by the new family. An old crate is not imported wholesale to preserve an obsolete boundary.

Twelve-answer rewrite gate

  1. What one question does it answer?
  2. What exact artifact does it own?
  3. What are its nearest false twins?
  4. Who owns every coordinate?
  5. What is the mathematical function or transition system?
  6. What are the exact public operations?
  7. What are the closed results and refusals?
  8. Which laws govern which operations?
  9. Which exact cross-owner contracts exist?
  10. What hostile case falsifies each law?
  11. How do old values remain interpretable?
  12. What evidence justifies implemented, conformant and certified?
A draft is rejected if any answer is “see repo sweep”, “per the Constitution”, “mixed class”, “borrowed template”, “structurally inapplicable” or “classification remains open”.

Structural-checker boundary

A checker may prove section presence, unique identifiers, operation/law cross-references and companion/index parity. It may not require fake ContextSpec records, R01–R44 restatement, decision algebras, C-gate tables, reviewer declarations or implementation ledgers inside every normative spec.

4.1 Five anti-multiplication rules

  1. A family may contribute to the shared compiler; it does not own a private application compiler/linker/registry.
  2. A native family plan is a rich semantic product only when real closure/conflict resolution exists; it is not generic application IR.
  3. A card is a versioned published contract for authored/selected/exchanged family data, not the universal container for every value.
  4. A law suite may be family-owned; harness and certificate vocabulary are shared. Empty/all-N/A suites cannot certify.
  5. A runtime is shared by progress algebra. A runtime heading is not automatically a process or crate.

8. Crate boundary gate

Begin with one crate and modules. A separate crate requires at least one strong reason and must name the consumer protected by the boundary:

  1. independently versioned public contract;
  2. materially different dependency or supply-chain profile;
  3. distinct durable-state/consistency/trust model that must be mechanically isolated;
  4. independent consumers that need only this surface;
  5. material compile-time, security, ownership or deployment isolation benefit.

“It has a heading,” “it may be useful later,” “the old toolkit had one,” and “the standard anatomy says so” are not reasons. The boundary collapses when the promised asymmetric consumer does not materialize.

10. First vertical and completion evidence

A completeness matrix over an empty application is insufficient evidence. After the shared descriptor and linker exist, select one named vertical that exercises identity, state, work, authority, sensitive data, temporal correction, integration, read models, evidence, lifecycle, UI and deployment.

10.1 Definition of done for a new library

  1. S0–S9 gates pass and R01–R44 have explicit dispositions.
  2. The ordinary Rust API works without the compiler/runtime.
  3. Every lawful decision is explicit; no branch requires a fork.
  4. Every seam has exact requirement, offer, typed satisfaction proof and refusal.
  5. All applicable DDD artifacts exist; all others are structurally inapplicable.
  6. Counts, manifests, schemas and documentation inventories derive from one descriptor source and drift checks fail closed.
  7. Minimal and maximal witness applications use the same implementation.
  8. The normative specification edition and digest are bound to the code and evidence revision.
  9. Certification status names only evidence actually produced.
