Use one universal contract for every sovereign specification, then apply a registry-specific profile. Do not create unrelated checklists for SEM, ONT, DAT, CMP, etc.; they would drift.
Call it the:
SAN Sovereign Specification Contract
SSPEC
Every specification must satisfy SSPEC. Registry profiles add stricter rules but cannot weaken it.
1. Universal SSPEC checklist
Every section is mandatory. If genuinely irrelevant, publish a typed INAPPLICABLE ruling with a reason and proof—never silently omit it.

2. Registry-specific profiles
SEM — reusable semantic family
Must additionally prove:
* Pure Rust owner library.
* No I/O, ambient time, randomness, environment or runtime loop.
* Native Rust API.
* Declarable decisions.
* Evolution and proof surfaces.
* Provider-neutral composition contracts.
* Direct construction and declaration construction converge on the same admitted semantic value.
* Cards, compiler pass, target IR and runtime parts exist only when semantically necessary.
* No duplicated ownership of another SEM concept.
ONT — business ontology
Must additionally prove:
* Business purpose and stakeholder language.
* Core/supporting/generic subdomain classification.
* Bounded contexts and context map.
* Entities, aggregates, roles and business policies.
* Business commands, decisions, events, workflows and invariants.
* Mapping from every generic concept to an existing SEM owner.
* No transport, database, framework or deployment semantics.
* No universal concept is re-owned locally.
ONT owns: “what this enterprise means”
SEM owns: “what reusable meaning means”
DAT — data and analytics domain
Must additionally prove:
* Data-product identity and owner.
* Input fact contracts and exact journal cuts.
* Event time versus recording time.
* Lineage and reproducibility.
* Quality rules and quarantine.
* Batch/streaming equivalence.
* Late, duplicate and out-of-order input behavior.
* Transformation DAG and incremental semantics.
* Metric/feature/model definitions.
* Serving and disclosure contracts.
* Backfill, correction, deletion and rebuild.
* Analytical outputs remain observations/proposals—not application facts.
* Mutations return through Chassis → Kernel.
CON — constitutional metamodel
Must additionally prove:
* Closed metamodel vocabulary.
* Nonforgeable authority and proof values.
* Requirement/contribution/offer algebra.
* Ownership, edition, compatibility and recall laws.
* Exact refusal and gap lifecycle.
* No package-selected authority can bootstrap itself.
* Independent Stage-0 authority boundary.
CMP — compiler/composition phase
Must additionally prove:
* Input/output artifact types.
* Ordered compilation stages.
* Checkpoints and resumability.
* Deterministic whole-input fingerprints.
* Decision closure.
* Provider/candidate selection.
* Obligation fixed-point closure.
* Gap and graph closure.
* Evidence and explanation retention.
* ApplicationClosure issuance criteria.
* Refused versus exhausted versus awaiting-selection outcomes.
TGT — target IR and lowering
Must additionally prove:
* Closed portable IR vocabulary.
* Validity rules.
* Semantic-preservation proof.
* Capability requirements.
* Target feature negotiation.
* Deterministic lowering.
* Unsupported lowering refusals.
* Source map and diagnostics.
* Backend equivalence and conformance vectors.
PRV — provider/adapter
Must additionally prove:
* Implemented port/contract.
* Provider capabilities and limits.
* Strict configuration schema.
* Health and readiness.
* Error normalization.
* Retry/idempotency behavior.
* Security and secret boundaries.
* Production eligibility.
* Conformance certificate.
* No provider-specific meaning leaks into SEM/ONT/DAT.
RUN — runtime
Must additionally prove:
* Boot state machine.
* Dependency wiring.
* Admission/authority/execution/egress phases.
* Single mutation path.
* Transaction/OCC/idempotency.
* Ledger/outbox/receipt.
* Effect execution after commit.
* Recovery and replay.
* Observability and cost.
* Production boot rejects unsafe defaults.
CTL — control plane
Must additionally prove:
* Desired versus observed state.
* Reconciliation state machine.
* Drift detection.
* Rollout/rollback.
* Health gates.
* Quotas and placement.
* Policy and authorization.
* Failure domains and backoff.
* Audit and operator explanation.
* No direct business mutation.

4. Mandatory verification gates
The verifier must reject:
duplicate stable identities
edition embedded in identity
unknown registry or dependency
dependency/ownership cycle
multiple semantic owners
undefined vocabulary terms
type without an owner
operation without exact signature
behavior without laws
decision without absence semantics
transition without refusal
authority-bearing value with public/raw constructor
unbounded work or allocation
batch work charged only per item
effect without a provider port
runtime mutation outside Kernel
analytical output presented as business fact
missing provenance/tenant/time/cut
unversioned schema
IR without validation
lowering without semantic-preservation evidence
certification without independent evidence
source/code operation-census mismatch
test-only authority presented as public conformance
5. Honest completion axes
Never use one complete Boolean. Publish these independently:
{
  "research_complete": false,
  "machine_source_complete": false,
  "source_verified": false,
  "operation_surface_complete": false,
  "semantic_execution_verified": false,
  "compiler_integration_verified": false,
  "lowering_verified": false,
  "runtime_vertical_verified": false,
  "independently_verified": false,
  "status": "REVIEW_CANDIDATE",
  "certification": "NONE"
}
This universal SSPEC plus registry profiles gives us one consistent method without pretending that a semantic algebra, business ontology, compiler phase and runtime adapter are the same kind of thing.
